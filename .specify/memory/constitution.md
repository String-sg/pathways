# Student Pathways Constitution

## Core Principles

### I. Public access and user-owned plans

Parents and young people MUST be able to explore without signing in. Saved plans MUST
use local export/import before introducing accounts or server storage. Do not collect
names, contact details, school, grades or personal results for product analytics.
An export MUST identify its rules version and the distinction between exam and
admission years. Private work stays on the device unless the user chooses to share it.

### II. Explain the limits of every result

The product MUST distinguish a planning illustration, application eligibility,
historical range, estimate and confirmed posting. Missing information MUST remain
unknown, not become a failing grade or a confident answer. Rules and material changes
MUST have dated official-source references and independently reviewed expected cases.
Agreement between implementations is a consistency check, not proof of correctness.

### III. Complete mobile journeys

Primary journeys MUST remain usable with touch, keyboard, enlarged text and narrow
screens. Essential explanations and unofficial-product notices MUST remain available
on mobile. Grey styling alone MUST NOT communicate that a feature is unavailable:
include a visible status and prevent misleading interactions.

### IV. Preserve provenance and working behaviour

Retain Evan Liao's Pathways adaptation, Mathew Lim's original model and prototype,
and Koo Tiannuo's Atlas contribution in visible credits and documentation. Preserve
Atlas source and its offline artifact while it is deferred in the public entry.
Do not consolidate engines until shared reference cases explain discrepancies.

### V. Bounded changes with honest evidence

Prefer the existing static architecture until a requirement justifies added services.
Specs MUST distinguish current behaviour, proposed work and verified results. Run
checks relevant to the changed behaviour and retain useful existing test coverage.
An unexecuted task, local screenshot or passing build MUST NOT be described as a
completed feature, verified admissions rule or production deployment.

## Product and Data Boundaries

Pathways is the first release priority. Atlas appears as a non-interactive
"Coming soon" placeholder; its implementation remains in the repository. Exported
summaries and editable plan files are the planned saving mechanism. Neon is deferred
unless a durable product requirement emerges. Any hosted GA4 integration MUST have
allowlisted coarse events, safe page metadata, verified stream settings and receipt,
and accurate privacy wording. Preserve a telemetry-free Atlas offline artifact.

## Development Workflow

Use constitution → specification → clarification → plan → tasks → analysis for a
bounded feature. Record assumptions and unresolved release dependencies explicitly.
Review the plan before application work beyond the authorised placeholder. Before
release, verify the intended deployment, sources, user journeys and privacy behaviour.
Keep feature specifications as living contracts and reconcile their tasks and test
matrix when scope changes.

## Governance

This baseline is proposed for adoption through the pull request. Amendments require a
recorded rationale and matching updates to affected specs, plans and verification.
Use major versions for incompatible principle changes, minor versions for new
principles and patch versions for clarifications. Reviews check compliance with the
current constitution; they do not silently relax it to accommodate implementation.
